# 银河麒麟 V10 与 V11 开启 SSH 远程协助：安装、防火墙与安全收尾

远程帮别人排查银河麒麟电脑时，最直接的方式之一，是在受控内网中临时开启 SSH，由协助人员登录终端查看日志、服务和配置。

V10 与 V11 的操作并不相同：V10 通常安装后即可使用；V11 的只读系统与维护模式增加了安装步骤，安全中心的网络区域还可能让“SSH 已启动，但外部仍连接失败”。

本文把两次实操指南合并成一篇，按版本给出流程，并补上安全收尾和常见故障判断。

> 实测环境：银河麒麟桌面 V10、V11 ARM64。V11 涉及 OSTree 只读系统、维护模式和安全中心防火墙。
> 记录时间：2026 年 8 月，V11 防火墙现象于 2026 年 9 月复测。不同小版本的界面和链名可能变化，应先查询再操作。

> [!warning] 只在可信网络中临时开放
> SSH 会带来远程登录入口。不要在不可信公共网络上按本文开放，也不要在路由器上把 22 端口映射到公网。优先使用临时账号或 SSH 密钥；不要把密码发到微信群、公开聊天或文章中。协助结束后关闭服务，并清理不再需要的防火墙规则和账号。

## 一、先看版本差异

| 项目 | 银河麒麟 V10 | 银河麒麟 V11 |
|---|---|---|
| 安装 OpenSSH | 正常桌面终端 | 本机需进入维护模式 |
| 是否重启 | 通常不需要 | 本流程需要两次 |
| 安装成果保留 | 常规系统写入 | 退出维护模式必须使用 `-c -a` |
| 防火墙 | 检查服务与监听 | 还要检查安全中心公网/内网链 |
| 后续再次开启 | 启动服务并确认 | 启动服务，并复查临时防火墙规则 |
| 完成后 | 关闭 SSH | 关闭 SSH，必要时移除临时规则 |

开始前保存工作、关闭文档。终端可用 `Ctrl+Alt+T` 打开，粘贴通常使用 `Ctrl+Shift+V`。输入密码时屏幕不显示字符，是 Unix 终端的正常行为。

## 二、V10：安装并启动 SSH

在正常桌面终端执行：

```bash
sudo apt update && sudo apt install -y openssh-server && sudo systemctl enable --now ssh
```

等待命令完成。如果软件源、网络或依赖报错，应先处理错误，不要继续把它当成已安装成功。

验证服务和监听：

```bash
systemctl is-active ssh
ss -tln | grep ':22'
```

预期看到：

- 服务状态为 `active`；
- 22 端口正在监听，地址可能是 `0.0.0.0:22`、`[::]:22` 或指定内网地址。

`active` 只说明服务运行，不代表网络一定能够到达。如果仍连不上，继续看本文防火墙和故障排查部分。

## 三、V11：通过维护模式安装

### 1. 进入维护模式

本机 V11 使用只读系统，需要在维护模式安装服务。先保存全部工作，然后执行：

```bash
sudo mm-cli -o
```

电脑会重启进入黑底白字的文字界面。出现 `login:` 后，输入开机用户名和登录密码。该界面通常不能使用指纹或人脸。

> 不同 V11 小版本的维护模式策略可能不同。如果系统正常桌面已允许安装，不需要为了照抄本文而额外进入维护模式。

### 2. 安装并启动

登录维护模式后执行：

```bash
sudo apt update && sudo apt install -y openssh-server && sudo systemctl enable --now ssh && systemctl is-active ssh
```

最后输出 `active`，才说明安装与启动阶段成功。

### 3. 保留成果并退出

执行：

```bash
sudo mm-cli -c -a
```

系统再次重启并返回正常桌面。

> [!important] 不要写错退出参数
> 本机实测使用 `-c -a` 保留安装成果。不要把 `-a` 写成 `-n`，否则可能放弃维护模式中的更改。执行前可用 `sudo mm-cli --help` 核对当前版本帮助信息。

## 四、V11 最容易漏掉的一步：防火墙

### 1. 服务正常，为什么仍连接失败

本机安全中心可能把办公 Wi-Fi 判为“公网”。公网入站策略未放行 22 端口时，会出现：

- `systemctl is-active ssh` 显示 `active`；
- 本机 22 端口正常监听；
- 对端 ping 收到 `Destination Host Prohibited`；
- SSH 报 `No route to host`。

这些现象说明数据包可能被本机防火墙拒绝，不一定是 SSH 服务故障。

### 2. 先查询网卡和规则

查看自己的无线网卡名：

```bash
ip -br link
ip -br -4 addr
```

原实测网卡为 `wlp2s0`，其他电脑可能不同。把下面的 `网卡名` 替换后再执行：

```bash
sudo iptables -S INPUT | grep '网卡名'
```

本次实测的判断方式：

- 进入 `KSC_PRIVATE_INPUT`：内网链，环境可能已放行 22；
- 进入 `KSC_PUBLIC_INPUT`：公网链，需要继续检查公网放行规则。

链名和默认策略由当前安全中心版本决定，不要只凭本文链名推断。继续查询：

```bash
sudo iptables -S KSC_IN_PUBLIC_ALLOW
sudo iptables -S KSC_PUBLIC_INPUT
```

如果链不存在，说明当前系统策略与实测环境不同，应改用安全中心界面或查询实际规则。

### 3. 临时放行，仅用于本次协助

确认当前确实走公网链、对端位于可信内网后，可临时允许 TCP 22：

```bash
sudo iptables -I KSC_IN_PUBLIC_ALLOW 1 -p tcp --dport 22 -j ACCEPT
```

随后立即让协助人员从对端连接验证。该规则可能在重启、防火墙重载或 Wi-Fi 重连后失效。

只放行 SSH 后，ping 仍被拒绝是可能的，不影响 SSH 本身。

### 4. 持久放行要谨慎

如果这台电脑长期位于可信办公内网，可在安全中心的网络防火墙或网络区域设置中，把当前网络调整为可信网络/内网。不同版本菜单名称可能不同。

不要把咖啡厅、酒店等公共 Wi-Fi 改成可信网络，只为省去一次防火墙配置。只是偶尔远程协助时，临时规则通常更容易控制影响面。

## 五、提供连接信息，但不要公开密码

查看用户名和 IP：

```bash
whoami
ip -br -4 addr
```

通常应提供当前内网网卡的 IPv4 地址，而不是 `127.0.0.1`。办公网 IP 可能动态变化，下次协助前应重新查询。

协助人员可在同一可信网络中测试：

```bash
ssh 用户名@内网IP地址
```

首次连接会显示主机指纹，应通过可信渠道核对，不要机械输入 `yes`。

认证优先级建议：

1. 为协助创建临时账号，结束后删除；
2. 使用专用 SSH 公钥，结束后移除对应授权；
3. 确需使用现有密码时，通过当面或电话等独立渠道传递，不发群聊，也不写入终端截图和文章。

## 六、协助结束后的安全收尾

### 1. 停止并禁用 SSH

在正常桌面执行，不需要进入维护模式：

```bash
sudo systemctl disable --now ssh
systemctl is-active ssh
```

预期不再是 `active`，常见结果为 `inactive`。

### 2. 删除临时防火墙规则

如果添加过本文的临时规则，先查看带编号的规则：

```bash
sudo iptables -L KSC_IN_PUBLIC_ALLOW --line-numbers -n
```

确认编号后删除对应规则：

```bash
sudo iptables -D KSC_IN_PUBLIC_ALLOW 规则编号
```

也可以按完整规则精确删除：

```bash
sudo iptables -D KSC_IN_PUBLIC_ALLOW -p tcp --dport 22 -j ACCEPT
```

如果同一规则添加过多次，需要重复检查。不要批量清空整条防火墙链。

### 3. 清理临时认证

若创建过临时账号或授权密钥，应在确认不再需要后删除。不要把临时入口留成长期后门。

## 七、下次再次需要协助

软件已经安装时，通常无需重装。V10 与已完成安装的 V11 都可先在正常桌面启动：

```bash
sudo systemctl enable --now ssh
systemctl is-active ssh
```

V11 再检查临时放行规则是否仍存在：

```bash
sudo iptables -S KSC_IN_PUBLIC_ALLOW
```

如果规则已失效、当前仍是可信内网且确需临时 SSH，再按前文添加。最后重新查询动态 IP：

```bash
whoami
ip -br -4 addr
```

完成后仍要执行“停止服务—删除规则—清理认证”的收尾流程。

## 八、常见故障怎么判断

| 现象 | 优先检查 | 说明 |
|---|---|---|
| `apt` 安装失败 | 软件源、网络、依赖和维护模式 | 未安装成功时不要继续查 SSH 配置 |
| `systemctl` 不是 active | `systemctl status ssh` 与日志 | 先解决服务本身 |
| active，但没有 22 监听 | `ss -tlnp` 与 sshd 配置 | 检查实际监听端口和地址 |
| 本机监听正常，对端超时 | 路由、网络隔离、对端 IP | 办公网可能禁止终端互访 |
| `No route to host` | 本机防火墙与网络区域 | V11 重点检查公网入站链 |
| ping 不通，但 SSH 可用 | ICMP 与 TCP 策略不同 | 不以 ping 作为唯一验证 |
| 密码正确仍拒绝 | 用户名、账号锁定、sshd 认证策略 | 不要反复盲目尝试触发锁定 |
| 重启后又连不上 | SSH 是否启用、临时规则是否丢失 | 重新检查服务和防火墙 |

服务日志可查看：

```bash
systemctl status ssh --no-pager
sudo journalctl -u ssh -n 80 --no-pager
```

日志可能包含用户名、IP 和系统路径，公开分享前应脱敏。

## 九、推荐用法：交给 AI 协助实施

这套流程同时涉及系统版本、维护模式、网卡、防火墙链和临时认证，不建议把命令原样发给不熟悉系统的用户逐条执行。可以把完整文章交给正在操作目标电脑的 AI 编程助手或终端智能体，让 AI 先判断环境，再协助实施。

可复制以下要求：

```text
请阅读这篇银河麒麟 V10/V11 开启 SSH 远程协助文章，协助我完成临时远程支持。

第一阶段只查询：确认系统版本、是否 OSTree 只读系统、OpenSSH 是否已安装、
ssh 服务状态、实际监听地址、网卡名称、内网 IPv4、防火墙链和网络区域。
不要立即安装软件、进入维护模式、修改防火墙或创建账号。

对比我的环境与文章实测环境，判断应走 V10 还是 V11 流程。V11 如需维护模式，
先说明会重启两次以及 -c -a 的作用；如果当前版本无需维护模式，不机械照抄。

只面向当前可信内网临时开放，不配置公网端口映射。优先建议临时账号或专用
SSH 密钥，不索要、显示或记录我的现有密码。执行安装、修改防火墙和重启前，
先列出改动、验证与回滚方法，等我确认。

连接成功后验证 SSH，而不仅用 ping 判断。协助结束后停止并禁用 ssh，删除本次
添加的临时规则、账号或密钥，再检查没有遗留入口。任何一步失败都停止并报告。
```

AI 应把“版本判断—最小开放—连接验证—安全收尾”串成完整流程，而不是只帮助开启服务。密码、私钥和完整环境变量不应进入提示词、日志或公开文章。

## 写在最后

V10 的核心是安装、启动和验证；V11 多了维护模式与安全中心防火墙两层。最常见的误判，是看到 SSH 为 `active` 就认为远程入口一定可用，或者 ping 不通就认为 SSH 一定不可用。

真正完整的远程协助流程，应同时包含：

1. 按版本正确安装；
2. 检查服务与实际监听；
3. 只在可信网络做最小范围放行；
4. 用 SSH 连接本身验证；
5. 结束后关闭服务并清理临时规则与认证。

远程协助的目标不是“永久能连”，而是“这次能连，结束后恢复干净”。
