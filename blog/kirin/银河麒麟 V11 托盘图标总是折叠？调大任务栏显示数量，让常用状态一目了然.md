# 银河麒麟 V11 托盘图标总是折叠？调大任务栏显示数量，让常用状态一目了然

![封面：任务栏托盘整排图标直接显示](../../assets/kylin-system-tray-more-icons-cover.png)

银河麒麟 V11 任务栏右下角的系统托盘，会显示输入法、音量、网络、蓝牙、电源以及各种应用的状态图标。装的软件一多，新图标就会被收进折叠区，每次都要点一下展开箭头才能看到。

我最初以为任务栏设置里会有"显示图标数量"之类的开关，翻遍控制中心却没有。查了 UKUI 的源码结构才发现：托盘能显示多少个图标，是由一个 QML widget 按宽度公式算出来的，系统根本没有暴露图形设置；直接改配置文件里的 `separateIndex` 也无效，原因后面会讲。

本文记录 2026 年 9 月在真机上完成的完整改造：通过**用户级 widget 覆盖**把托盘容量从默认的几个扩大到约 20 个，并让新图标自动留在显示区。全程不碰只读系统分区、不需要 root、不需要维护模式，删一个目录即可完全恢复。

> [!warning] 这是非官方修改，先看清楚再动手
> 本文修改的是 UKUI 托盘 widget 的 QML 源码副本，属于非官方定制，系统升级后行为可能变化。所有改动只在用户家目录 `~/.local/share/` 下，不写 `/usr`、不需要 root，可一键恢复。请先通读"残留瑕疵"一节，确认能接受后再操作；生产或涉密机器建议先在测试机验证。

## 一、背景：图标为什么会被折叠

UKUI 的系统托盘由包 `ukui-widget-system-tray` 提供，是一个 QML widget，源码位于：

```text
/usr/share/ukui/widgets/org.ukui.systemTray/
├── metadata.json
├── translations/
└── ui/
    ├── main.qml          # widget 入口，注册到面板
    ├── TrayView.qml      # 显示区/折叠区分组、容量计算
    ├── FoldArea.qml      # 折叠弹层
    ├── ControlPanel.qml  # 音量/网络等控制面板项
    └── TrayIcon.qml      # 单个图标
```

托盘内部分两组：**显示组（Show）**直接排出来，**折叠组（Fold）**收在箭头弹层里。两组的分界由 C++ 侧 `ItemModel` 的 `currentSeparateIndex` 决定，并持久化在：

```text
~/.config/org.ukui/_ukui-config-global/org.ukui.systemTray.json
```

我在控制中心和任务栏右键菜单里反复找过，本机版本**没有任何调节托盘图标数量的图形项**（对 `/usr/share/ukui-control-center/` 全文检索也找不到相关设置）。所以只剩两条路：忍受，或者改 widget。

## 二、环境信息与修改范围

| 项目 | 实测环境 |
|---|---|
| 系统 | 银河麒麟桌面 V11 ARM64，OSTree 只读系统 |
| 面板 | ukui-panel `4.21.0.0` |
| 托盘组件 | ukui-widget-system-tray `4.21.0.2` |
| 显示协议 | Wayland，双屏 |
| 面板高度 | 50px（本机自定义值；面板配置中的默认值为 48px） |

修改范围（全部在用户家目录内）：

- 新增目录：`~/.local/share/ukui/widgets/org.ukui.systemTray/`（从 `/usr` 复制后修改其中 2 个文件）
- 不修改 `/usr` 下任何文件，不使用 `sudo`，不进入维护模式
- 恢复方式：删除该目录并重启面板（见第八节）

UKUI widget 框架的搜索路径中，`~/.local/share/ukui/widgets` **优先于** `/usr/share/ukui/widgets`，所以家目录里的同名 widget 会直接覆盖系统版，这正是本方案免 root 的基础。其他小版本如果目录结构一致，原理同样适用，但公式参数需要自行核对。

## 三、先搞懂原理：三个关键机制

动手前先理解三件事，否则后面的代码会变成玄学。

### 1. 容量是按宽度公式算出来的

`TrayView.qml` 的 `getShowCount()` 用官方公式计算最多能直接显示多少个图标：

```javascript
showCount = (maxLength - (controlPanelLength - itemShort))
            / (itemShort + viewSpacing) - 2
```

面板高度 50px、缩放因子约 1.0417 时，单个图标宽 `itemShort ≈ 33.3px`、间距 `viewSpacing = 0`、控制面板段 `controlPanelLength ≈ 62px`。默认的 `maxLength` 很小，算下来只能直接显示几个图标，其余全部进折叠组。

### 2. maxLength 来自面板容器，不在 widget 自己身上

`maxLength` 绑定的是宿主容器（C++ 侧）挂在 widget 根节点父级上的 `Layout.maximumWidth`。widget 自身该属性的默认值是 `INT_MAX`，直接改它没有任何效果；必须在运行时拿到宿主对象、改写宿主的 `Layout.maximumWidth`，绑定变化才会传播进 `TrayView`。

### 3. separateIndex 只是"分界"，手改 JSON 没用

配置文件里的 `separateIndex` 是显示组与折叠组的分界序号，**不是容量开关**。手工编辑它无效，有三个原因：

1. 显示组受 `showCount` 上限约束，分界写到容量以上照样显示不出来；
2. UKUI 的官方设计是**新注册的 SNI 图标默认落在分界之后**，即新图标默认折叠，只放大容量不会让它们自动出来；
3. 面板运行时会用内存里的值回写 JSON，手工改动会被覆盖。

所以完整方案必须同时做两件事：**放大容量（改 `maxLength`）+ 自动把分界推到图标总数（调 `setSeparateIndex`）**。

## 四、操作步骤

### 第 1 步：把系统 widget 复制到用户目录

```bash

if [ -d ~/.local/share/ukui/widgets/org.ukui.systemTray ]; then
  tar czf ~/ukui-systemtray-custom-backup.tar.gz \
      -C ~/.local/share/ukui/widgets org.ukui.systemTray
fi

# 同时留存托盘分界与排序配置
cp -a ~/.config/org.ukui/_ukui-config-global/org.ukui.systemTray.json \
      ~/org.ukui.systemTray.json.before

mkdir -p ~/.local/share/ukui/widgets
cp -r /usr/share/ukui/widgets/org.ukui.systemTray \
      ~/.local/share/ukui/widgets/
```

复制后所有修改都在 `~/.local/share/ukui/widgets/org.ukui.systemTray/ui/` 内进行。系统原版留在只读分区里，随时可以对照。

### 第 2 步：修改 main.qml，给托盘一个固定最大宽度

编辑 `~/.local/share/ukui/widgets/org.ukui.systemTray/ui/main.qml`，在 `WidgetItem` 内加入一个 100ms 定时器：启动后轮询宿主的 `Layout.maximumWidth`，拿到合理基值（用 `100 < v < 20000` 排除 `INT_MAX` 默认值）后写入固定值 **775**，写完即停。垂直面板同理处理 `maximumHeight`。

完整文件如下（在官方原版基础上只增加了注释标出的部分）：

```javascript
import QtQuick 2.15
import QtQuick.Layouts 1.15
import org.ukui.quick.widgets 1.0
import org.ukui.quick.items 1.0

WidgetItem {
    id: root
    property bool isHorizontal: (Widget.orientation === Types.Horizontal)
    property int pos: Widget.container.position
    property real ratio: parent.ratio ? parent.ratio : 1
    // 主副屏托盘容量统一为约 20：面板高 50 时单图标 33.3px、控制面板 62px，
    // host 最大宽 775 → showCount=(775-28.7)/33.3-2≈20.4→20。
    // 托盘实际宽度仍等于内容宽度，不会因此多占面板空间。
    property int targetCapacity: 775
    property int baseMaxW: 0
    property int baseMaxH: 0

    // —— 以下 Timer 为新增部分 ——
    Timer {
        id: capTimer
        interval: 100
        running: true
        repeat: true
        onTriggered: {
            let host = root.parent
            let got = false
            if (host) {
                if (root.isHorizontal) {
                    let pw = host.Layout.maximumWidth
                    if (root.baseMaxW === 0 && pw > 100 && pw < 20000) {
                        root.baseMaxW = pw
                        host.Layout.maximumWidth = root.targetCapacity
                        got = true
                    }
                } else {
                    let ph = host.Layout.maximumHeight
                    if (root.baseMaxH === 0 && ph > 100 && ph < 20000) {
                        root.baseMaxH = ph
                        host.Layout.maximumHeight = root.targetCapacity
                        got = true
                    }
                }
            }
            if (got)
                stop()
        }
    }
    // —— 新增部分结束 ——

    Layout.fillWidth: !isHorizontal
    Layout.fillHeight: isHorizontal
    Layout.preferredWidth: childrenRect.width
    Layout.preferredHeight: childrenRect.height
    Layout.minimumWidth: isHorizontal ? dropArea.controlPanelLength + dropArea.itemShort : -1
    Layout.minimumHeight: isHorizontal ? -1 : dropArea.controlPanelLength + dropArea.itemShort
    clip: true
    Widget.active: dropArea.panelActive

    TrayView {
        id: dropArea
        property bool panelActive: false
        property bool onTopBar: parent.height < 40
        scaleFactor: parent.ratio
        isHorizontal: parent.isHorizontal
        itemWidth: onTopBar ? 28 : isHorizontal ?
                                  scaleFactor * 32 : scaleFactor * 40
        itemHeight: onTopBar ? 28 : isHorizontal ?
                                   scaleFactor * 40 : scaleFactor * 32
        itemLong: onTopBar ? 28 : scaleFactor * 40
        itemShort: onTopBar ? 28 : scaleFactor * 32
        panelPos: parent.pos
    }

    onWidthChanged: {
        dropArea.changeFoldWindowPosition();
    }

    onHeightChanged: {
        dropArea.changeFoldWindowPosition();
    }
}
```

**775 这个数是怎么标定的？** 把目标容量 20 代回官方公式反推：

```text
maxLength = (20 + 2) × 33.3 + (62 − 33.3) ≈ 761
```

取 775 留少量余量，正算结果 `(775 − 28.7) / 33.3 − 2 ≈ 20.4`，取整为 20。注意这里用的是**固定值而不是"基值 × 系数"**：我早期试过乘 1.5 系数，结果主屏只能放 17 个、副屏放到 22 个，两块屏容量不一致会引发后面要讲的双屏打架问题；固定 775 让两屏算出来的容量完全相同。

另外不用担心 775 会把任务栏撑宽——`Layout.preferredWidth` 仍然绑定 `childrenRect.width`，托盘实际宽度永远等于内容宽度，775 只是放宽了上限。

### 第 3 步：修改 TrayView.qml，自动展开折叠图标

编辑 `~/.local/share/ukui/widgets/org.ukui.systemTray/ui/TrayView.qml`。

首先，`getShowCount()` **保持官方公式原样，不要再乘任何系数**（双重放大曾把图标数推到 28 个）：

```javascript
function getShowCount() {
    dropArea.showCount = (maxLength - (controlPanelLength - dropArea.itemShort))
                         / (dropArea.itemShort + trayview.viewSpacing) - 2;
}
```

然后在它下面新增"自动展开 + 重试收敛"逻辑：

```javascript
// 新图标默认落在持久化分界 separateIndex 之后进折叠区；
// 只要总数未超容量，就把分界推到总数，使全部图标留在显示区。
function autoShowHidden() {
    let inShow = showModel.rowCount();
    let inFold = foldModel.rowCount();
    let total = inShow + inFold;
    if (inFold > 0 && total <= dropArea.showCount)
        ItemModel.setSeparateIndex(total);
}

// 双屏各有一个 TrayView 实例、共享底层数据，分界写入可能被另一实例覆盖，
// 因此信号到来后延迟纠正并在未稳定时重试，直到本组 fold 真正清零。
Timer {
    id: settleTimer
    interval: 120
    repeat: false
    property int tries: 0
    onTriggered: {
        dropArea.autoShowHidden();
        tries++;
        if (foldModel.rowCount() > 0
            && foldModel.rowCount() + showModel.rowCount() <= dropArea.showCount
            && tries < 25)
            start();
    }
}
function scheduleSettle() { settleTimer.tries = 0; settleTimer.start(); }

Connections { target: showModel; onRowsInserted: dropArea.scheduleSettle() }
Connections { target: showModel; onRowsRemoved: dropArea.scheduleSettle() }
Connections { target: showModel; onModelReset: dropArea.scheduleSettle() }
Connections { target: showModel; onCurrentSeparateIndexChanged: dropArea.scheduleSettle() }
Connections { target: foldModel; onRowsInserted: dropArea.scheduleSettle() }
Connections { target: foldModel; onRowsRemoved: dropArea.scheduleSettle() }
Connections { target: foldModel; onModelReset: dropArea.scheduleSettle() }
Connections { target: foldModel; onCurrentSeparateIndexChanged: dropArea.scheduleSettle() }
onShowCountChanged: scheduleSettle()
Timer { interval: 1000; running: true; repeat: false; onTriggered: dropArea.scheduleSettle() }
```

这里有两个 C++ 接口细节，是读源码确认的，写错就静默失效：

- `GroupModel` **没有 `count` 属性**，`rowCount` 是 `Q_INVOKABLE` 方法，QML 里必须带括号写成 `showModel.rowCount()`；
- 分组模型**不发 `rowCountChanged` 信号**，只能监听 QAbstractItemModel 标准信号 `rowsInserted / rowsRemoved / modelReset`，以及分界变化信号 `currentSeparateIndexChanged`；
- `Connections` 不能放进 `for` 循环里批量创建，必须像上面这样逐个展开写。

当折叠组清空时，`FoldArea` 的 `onIsEmptyChanged` 会自动隐藏折叠按钮，不需要额外处理。

### 第 4 步：重启 ukui-panel

QML 改动需要重启面板才生效。注意一个坑：**`pkill` 掉 ukui-panel 后，会话不一定会自动把它拉起来**，需要手动启动，并 `setsid` 脱离当前终端进程组：

```bash
pkill -x ukui-panel
sleep 3
setsid ukui-panel >/dev/null 2>&1 </dev/null & disown
sleep 2
pgrep -x ukui-panel
```

最后一条命令能输出进程号，说明面板已起来。任务栏会闪烁几秒后恢复，属于正常现象。

### 第 5 步：验证效果

三个层面依次确认：

1. **肉眼看**：折叠箭头消失，输入法、音量、网络、蓝牙及各应用图标全部直接排列在托盘里；
2. **看分界值**：`separateIndex` 应等于当前图标总数（我机器上 12 个图标时它就是 12），证明自动展开生效：

```bash
grep -n 'separateIndex' \
  ~/.config/org.ukui/_ukui-config-global/org.ukui.systemTray.json
```

3. **看资源占用**：用 `ps -o %cpu= -C ukui-panel` 观察面板稳态 CPU，并与修改前比较。启动瞬间升高不代表异常；如果持续处于很高占用（本机排错时曾达到 80% 以上），多半是定时器代码抛异常没能 `stop()`，见下一节。

## 六、坑点与排错

### 1. 双屏两个 TrayView 实例抢写分界

每块屏的面板各跑一个 `TrayView` 实例，但底层 `ItemModel` 数据是共享的。两个实例算出的 `showCount` 只要不同，就会互相覆盖 `separateIndex`：日志里能看到一个实例刚写成 11，75ms 后另一个写回 10，折叠组始终剩 1 个图标，还可能呈现"空折叠区"。

**对策**：用固定 775 让两屏容量完全一致，再靠 `settleTimer` 重试到折叠组真正清零为止（上限 25 次，每次 120ms，约 3 秒内收敛）。

### 2. 容量公式只能改一次，不要双重放大

早期方案在 `main.qml` 放大宿主宽度的同时，又在 `getShowCount()` 里乘了 1.5 系数，两边叠加直接把容量推到 28 个，托盘挤爆。最终方案里 `getShowCount()` 保持官方公式，所有放大只通过宿主宽度这一个入口完成。

### 3. 定时器引用未定义对象会导致 CPU 跑满

定时器成功分支里如果引用了不存在的对象、且异常发生在 `stop()` 之前，定时器会永远重复触发，面板 CPU 飙到 85%~109%。改完代码先用 `ps -o %cpu= -C ukui-panel` 看稳态占用；启动瞬间 100% 是正常的，持续不降才有问题。

### 4. pkill 后面板不自动重启

某些会话配置下 `pkill -x ukui-panel` 后面板不会被守护进程拉起，任务栏直接消失。不要慌，用第四节的 `setsid ukui-panel ...` 手动拉起即可，养成 kill 之后立刻 `pgrep` 确认的习惯。

### 5. FoldArea 官方缺陷导致折叠图标偶尔为 null

官方 `FoldArea.qml` 对正在注册中的图标直接访问 `model.ToolTipTitle.length`，会抛 TypeError（官方代码的问题，不是本方案引入的）。表现是折叠弹层里偶现空图标，把图标拖到显示区即消失。**不要去改官方这段逻辑**，折叠组清空后折叠按钮本身会隐藏，正常使用碰不到它。

### 6. 手改 separateIndex 为什么白费功夫

再强调一次：`separateIndex` 是分界不是容量。容量受 `showCount` 公式卡死，新图标默认进折叠组，且运行中的面板会回写 JSON。只改 JSON 不改 widget，三件事一件都解决不了。

## 七、残留瑕疵与适用边界

如实列出本方案的不完美之处，接受再用：

1. **用户副本是固定快照**：系统更新 `ukui-widget-system-tray` 后，家目录里的副本不会自动跟随新版，需要重新复制并重新打补丁；
2. **775 与面板尺寸绑定**：如果改过面板高度、显示缩放，`itemShort` 和 `controlPanelLength` 都会变，需要按第三节的公式重新标定 `targetCapacity`；
3. **手动折叠会被自动拉回**：`autoShowHidden` 的代价是你手动拖进折叠区的图标会被立刻拉回显示区。想彻底隐藏某个图标，要到该应用自身设置里关闭托盘图标（自启项一般在 `/etc/xdg/autostart/`）；
4. **版本差异**：本文基于 ukui-panel 4.21.0.0 / ukui-widget-system-tray 4.21.0.2。其他版本若 widget 目录名、QML 结构或 C++ 接口不同，需要先读对应源码再调整，不能无脑照抄。

## 八、一键恢复

因为不碰 `/usr`，恢复就是删掉用户副本再重启面板，系统原版立即生效：

```bash
rm -rf ~/.local/share/ukui/widgets/org.ukui.systemTray
pkill -x ukui-panel
sleep 3
setsid ukui-panel >/dev/null 2>&1 </dev/null & disown
```

无需清理 `/usr` 或包管理，也不需要维护模式。`separateIndex` 和图标排序等用户状态仍可能保留，但系统原版会按默认容量重新分组；如果还需要恢复原来的分界与排序，可在面板未运行时谨慎恢复第一步备份的 `org.ukui.systemTray.json.before`。若只需撤销扩容，不必恢复这个 JSON。

建议操作前按第一步备份已有的用户副本和托盘配置；首次使用、还没有用户副本时，不需要凭空创建备份。

## 写在最后

这次改造最值得记录的，其实不是具体代码，而是定位问题的路径：图形设置里找不到开关，不等于需求无法实现——沿着 widget 目录、QML 公式和 C++ 模型接口往下读，能看到"容量由宽度公式决定、分界由 separateIndex 决定、新图标默认折叠"这三层机制，方案自然就浮现出来了。

而 OSTree 只读系统也不等于只能忍受默认行为：UKUI 的 widget 搜索路径给用户级覆盖留了正规入口，让定制完全发生在家目录里，可复制、可恢复、不碰包管理。把改动限制在这一层，既是技巧，也是安全边界。
