# Betterbird 大附件“另存为”卡顿排查与修复

一封邮件里有一个约 44 MB 的压缩包。我在 Betterbird 140 中点击附件“另存为”，界面随即长时间没有响应。

这类问题很容易被概括为“客户端卡死了”，但直接强杀进程可能让事情更糟：附件是否还在写、邮件数据库是否正在更新、再次打开后会不会留下临时文件，都不好判断。

这次处理分成了两条线：

1. **先拿到附件**：不等界面恢复，从本地 POP3 的 mbox 邮件文件中只读提取目标附件，并校验压缩包完整性；
2. **再解决根因**：检查磁盘、CPU、安全软件扫描和 Betterbird 的附件保存实现，最后在保留旧程序和关键配置备份的前提下升级到 153。

升级后，中文界面、邮件、模板扩展和大附件保存均通过验证。本文保留完整排查与回退过程，同时纠正原排障笔记中的一处官方 Bug 引用错误。

> 实测时间：2026 年 9 月 21 日。环境为银河麒麟 V11 ARM64（飞腾 D3000，8 核）、glibc 2.38、Wayland 会话。原始操作由 Qwen Code 协助完成，本文是个人实测复盘，不代表所有版本和发行版都有相同表现。

## 一、先说结论：不是磁盘慢，也不像真正死锁

本次卡顿由多项因素叠加：

- Betterbird/Thunderbird 140 的附件保存流程需要在主线程完成较重的 MIME 解析和解码；
- 当时本机源码分析显示，保存附件后还会为下载记录再次处理同一附件，进一步放大等待时间；
- 另一个应用的两个工作线程长期各占满一个 CPU 核，8 核机器持续损失约四分之一算力；
- 安全软件实时防护会在附件落盘时同步扫描，再增加一些等待。

磁盘和空间反而不是问题：实测写入约 1.4 GB/s，剩余空间约 383 GB；单独做 44 MB 数据的 Base64 解码只需约 0.17 秒。这个对照说明，不能把 Base64 解码本身的理论耗时等同于整条邮件从 mbox 定位、MIME 解析到附件写盘的总耗时。

因此，本次更准确的说法是：**保存流程仍在工作，但主线程被重任务占住，界面表现为“假死”。**

如果再次遇到类似情况，先观察进程 CPU 和磁盘活动。只要任务仍有进展，就不要第一时间强杀；也可以尝试把附件直接拖到目标目录，或使用“全部保存”，比较不同入口的表现。

## 二、先应急提取附件：绕过界面，不改邮件库

当时最急的是先拿到压缩包。Betterbird 的 POP3 邮件以 mbox 形式保存在实际使用的 Profile 中，所以可以直接从本地邮件文件提取。

### 1. 先确认活跃 Profile

本机实际使用的是：

```text
~/.betterbird-profile/
```

旧的 `~/.thunderbird/` 只是历史副本，不是当前数据。这是第一个容易踩的坑：如果读错 Profile，可能耗费很长时间扫描旧邮件，却找不到目标邮件。

POP3 收件箱位于当前 Profile 的 `Mail/<POP账号目录>/Inbox`。公开版不保留真实服务器目录名；实际操作时，应在客户端的账户设置或配置目录中确认自己的路径。

### 2. 中文标题不能直接 grep

目标邮件使用中文标题，但 mbox 中的标题可能按 RFC 2047 编码，例如：

```text
=?gb2312?B?...?=
```

因此，直接对 mbox 执行中文 `grep` 往往找不到。此次采用 Python 标准库 `email` 处理：

1. 按 mbox 的消息分隔行扫描文件；
2. 先只解析头部，用 `email.header.decode_header()` 和 `make_header()` 解码主题、发件人；
3. 定位目标邮件后，记录它在文件中的字节偏移和长度；
4. 用 `seek(offset)` 精确读取这一封邮件，不再反复扫描整个收件箱；
5. 遍历 `msg.walk()`，对带文件名的 MIME part 执行 `get_payload(decode=True)`，将附件写入新的输出文件。

核心不是某一段固定脚本，而是**先解码头部定位，再按偏移只读提取**。这样既避免界面卡顿，也不需要修改 mbox。

> [!warning] 数据安全边界
> 提取前应完全退出邮件客户端，避免它同时写入邮箱；只读打开 mbox，附件另存到独立输出路径。不要直接编辑、截断或“修复”原始 Inbox，也不要把真实邮件和名单上传到公共 AI。

### 3. 提取后必须验证文件

本次提取得到约 44 MB 的 ZIP 文件，随后做了两类检查：

- 记录文件字节数和 SHA-256，确认后续传递的是同一份文件；
- 使用 `unzip -t` 校验压缩包，结果完好，内部文档数量与邮件内容相符。

“文件已经写出来”不等于“附件提取成功”。尤其是界面曾经卡住时，完整性校验不能省。

## 三、为什么 140 的“另存为”会占住界面

### 1. 主线程承担了整条消息的重处理

当时检查 `comm-esr140` 的 `mail/modules/AttachmentInfo.sys.mjs`，重点看了 `saveToFile()` 的调用链。

本机源码分析显示，附件通过 `NetUtil.asyncFetch` 获取后，libmime 仍需对消息进行 MIME 解析和 Base64 解码；`readInputStream` 还会把附件内容读入内存再写盘。虽然网络或文件获取带有异步接口，但这不等于整条处理链都离开了主线程。

对小附件，这点等待通常不明显；附件增大、邮箱文件较大、CPU 又繁忙时，界面无响应就会被明显放大。

### 2. 下载记录带来了第二次处理

当时的源码阅读和实际操作还发现：附件第一次写盘后，程序又通过 `Downloads.createDownload(...).start()` 创建下载任务，以便把文件登记到“已保存文件”列表。这个分支会再次抓取、解码并写入临时文件，再完成改名。

也就是说，本次 140 环境中的大附件保存不是简单的“解码一次、写盘一次”，重复处理让开销进一步增加。升级到 153 后，本机观察到的重复写盘现象消失。

### 3. 一处必须纠正的官方引用

原始排障笔记曾把上述重复处理归因于 Mozilla **Bug 1993854**，并进一步写成“官方承认重复写盘、146 起修复”。公开整理时重新打开该页面核验，发现它实际讨论的是：

> 通过“Open with”打开 Microsoft Office 附件时的安全处理，以及保存文件来源标记。

该 Bug 的目标里程碑确实是 146 Branch，但它的主题并不是本文所说的大附件重复解码和写盘。因此，本文**不再用它证明重复写盘机制，也不保留“146 起修复该性能问题”的官方结论**。

这里保留两个层次不同的结论：

- **个人源码分析与实测**：本机 140 存在重复处理，升级到 153 后该现象消失；
- **官方资料**：Betterbird 的发布说明可用于核对版本和变更，Bug 1993854 不能作为本文性能根因的直接证据。

原始 Bug 页面仍列在这里，便于读者核验这次纠正：<https://bugzilla.mozilla.org/show_bug.cgi?id=1993854>。

## 四、本机环境因素：放大问题，但不是单独根因

### 1. 两个工作线程长期占满 CPU

排查时发现，另一个应用的两个工作线程各自持续占满一个核，已运行约 8 小时。对 8 核机器来说，相当于长期损失约四分之一算力。

这是该应用自身的异常状态，重启后恢复。它能解释为什么附件保存更慢，却不能单独解释 Betterbird 140 的保存流程为何占住界面。

### 2. 实时防护增加落盘等待

安全软件会在附件写盘时进行同步扫描。大文件、压缩包和多层文档都可能增加扫描开销。这属于叠加因素，不建议为了保存附件就长期关闭实时防护。

### 3. 已排除的项目

本次实测未发现以下问题：

- 磁盘写入瓶颈或空间不足；
- 残留的 `.part` 文件；
- 桌面启动器或扩展冲突；
- 客户端崩溃记录。

这些结果只代表当时这台机器，不能据此排除其他设备上的磁盘、扩展或崩溃问题。

## 五、升级前先核对 153 的兼容性

本次不是直接覆盖安装，而是先确认程序架构、语言包、扩展和 Profile 回退条件。

| 项目 | 当时核验结果 |
|---|---|
| Betterbird 153 ARM64 包 | 实际使用 `betterbird-153.3.0esr-bb9.en-US.linux-aarch64.tar.xz` |
| 构建要求 | 当时下载包对应 glibc 2.36，本机 glibc 2.38 满足 |
| 简体中文语言包 | 使用与 153 对应的 `zh-CN-153.3.0esr-bb9.xpi` |
| TemplateWing | 本机官方版 2.9.0，所用 API 在 153 schema 中逐项核对存在 |
| Manifest V2 | 当时 153 schema 允许 `manifest_version` 2～3 |
| Profile 密码数据 | 官方发布说明明确提示 140→153 间加密方式变化，降级需重输密码或恢复旧密码文件 |

Betterbird 153.3.0esr-bb9 的官方发布日期是 **2026 年 9 月 16 日**，与本文 9 月 21 日的升级时间相符：

- 发布公告：<https://blog.betterbird.eu/2026/09/release-15330esr-bb9>
- 发布说明：<https://www.betterbird.eu/releasenotes/>
- 官方下载入口：<https://www.betterbird.eu/downloads/>

这些链接用于核对版本，不表示文章发布后仍应下载 153.3。实际升级时，应从官方页面选择当前版本，并重新检查架构、glibc、语言包和扩展兼容性，不要照抄本文旧文件名。

### TemplateWing 2.9.0：旧私人补丁可以退役

本机此前为了按邮箱匹配通讯录真实姓名，维护过基于 TemplateWing 2.8.0 的私人补丁。升级前重新核对时发现，官方 2.9.0 已具备相应能力，不再需要继续维护旧补丁。

TemplateWing 2.9.0 的官方发布说明也明确提到：没有显示姓名的地址会从匹配联系人中取得姓名，同时保留收件人已有的显示姓名。发布页还列出了昵称变量、模板不再覆盖已选收件人等变化：

<https://github.com/JuliaKalder/TemplateWing/releases>

这次经验很重要：**扩展排查要以本机当前 manifest、代码和官方发布说明为准，不能沿用上一次升级时的记忆。**

## 六、升级执行：新程序独立目录，旧版本不覆盖

本次所有程序改动都在用户目录内，Betterbird 140 旧程序保持不覆盖。

### 1. 退出客户端并确认目标路径

先完全退出 Betterbird，确认没有后台进程仍在写 Profile。本文路径对应本机实测：

```text
~/Applications/Betterbird/                 140 旧程序
~/Applications/betterbird-153/             153 新程序
~/Applications/betterbird-153-dist/        安装包与语言包
~/.betterbird-profile/                     原 Profile
```

读者应替换为自己的实际路径，不要机械复制目录名。

### 2. 下载并校验安装包

当时将 ARM64 程序包和 153 中文语言包下载到 `~/Applications/betterbird-153-dist/`，随后：

- 用 `xz -t` 检查程序压缩包；
- 用 `unzip -t` 检查 XPI 语言包；
- 核对文件字节数与下载来源信息。

语言包不能使用 140 的旧版本替代 153 对应版本。即使扩展 ID 相同，也要检查 manifest 中的严格兼容范围。

### 3. 备份 Profile 关键配置

升级前备份了约 70 MB 的关键文件，包括：

- `prefs.js`、`user.js`；
- `extensions.json`；
- `key4.db`、`cert9.db`、`logins.json`；
- 各 SQLite 数据库。

备份目录为 `~/Applications/bb140-profile-keyconfig-backup-20260921/`。这些文件含有账户、证书和密码相关数据，不能上传到公开仓库或交给公共 AI。

### 4. 解压到独立程序目录

将程序解压到 `~/Applications/betterbird-153/`，使用 `--strip-components=1` 去掉压缩包顶层目录。语言包放到该版本自己的应用级扩展目录：

```text
~/Applications/betterbird-153/extensions/langpack-zh-CN@betterbird.eu.xpi
```

本机 `user.js` 已包含语言包签名相关设置，因此没有再次修改系统配置。这个设置会降低语言包签名校验要求，只能用于来源明确的官方语言包；如果当前官方版本已经能够正常签名注册，应恢复默认安全策略。

### 5. 用原 Profile 启动 153

第一次启动仍显式指定原 Profile：

```bash
"$HOME/Applications/betterbird-153/betterbird" \
  -profile "$HOME/.betterbird-profile" -no-remote
```

验证通过后，才把桌面启动器切换到新程序。旧启动器提前备份为：

```text
~/Applications/Betterbird.desktop.bb140-20260921
```

这个顺序保证了“程序可独立回退、启动入口也可独立回退”，不需要先卸载旧版本。

## 七、验证结果：不仅看能不能启动

本次升级后逐项检查：

- 简体中文界面正常；
- 收件箱及各邮件文件夹内容完整；
- TemplateWing 回复模板抬头插入正常；
- 按邮箱匹配通讯录真实姓名正常；
- 模板快捷键 `Ctrl+Shift+1` 正常；
- 桌面启动器通过 `desktop-file-validate` 校验；
- 大附件保存不再出现此前观察到的重复写盘。

邮件客户端升级不能只看主窗口是否出现。真正需要验证的是：**数据是否完整、关键扩展是否仍按原习惯工作、原始故障是否消失、启动入口是否指向预期版本。**

## 八、回退方法：程序容易退，密码数据要提前准备

如果 153 验证不通过，本次预案如下：

1. 完全退出 Betterbird 153；
2. 恢复旧桌面启动器：

```bash
cp "$HOME/Applications/Betterbird.desktop.bb140-20260921" \
  "$HOME/Desktop/Betterbird.desktop"
```

3. 用旧程序和原 Profile 启动：

```bash
"$HOME/Applications/Betterbird/betterbird" \
  -profile "$HOME/.betterbird-profile" -no-remote
```

4. 如果旧版本无法读取升级后的密码数据，从升级前备份恢复 `key4.db`、`cert9.db` 和 `logins.json`，或按官方提示重新输入密码。

Betterbird 官方发布说明明确提醒：140 与 153 之间 `logins.json` 的用户名和密码加密方式发生变化，降级时需要重新输入密码，或恢复先前备份。邮件数据与密码库是两类问题，不要把“邮件还在”误认为“所有配置都能无损降级”。

稳定使用一两周后，可以按自己的备份制度清理旧程序、安装包和旧启动器副本；关键配置备份的保留周期应结合实际需要决定，不建议升级刚成功就立即删除。

## 九、这次排查还留下的两个经验

### 1. Wayland 下不要只信 X11 窗口工具

本机是 Wayland 会话，Betterbird 使用原生 Wayland 后端时，`wmctrl`、`xdotool` 等 X11 工具可能查不到它的窗口。这不等于客户端没有启动。

排障时应直接确认屏幕状态、进程和日志，不要把工具协议不支持误判为程序异常。

### 2. 大附件问题先保数据，再谈优化

从 mbox 提取附件不是日常保存的替代方案，而是界面无法响应时的应急通道。它之所以可靠，是因为做到了：

- 找到真正的活跃 Profile；
- 正确处理编码后的邮件头；
- 按偏移读取目标邮件；
- 不修改原始邮箱；
- 对输出附件做完整性验证。

先拿到并验证数据，后面的源码分析和版本升级就不必在“工作被卡住”的压力下仓促进行。

## 十、推荐用法：交给 AI 协助实施

> [!important]
> 邮件、附件、Profile 和密码数据库都可能含有敏感信息。只让 AI 使用虚构样例或本机只读结果，不要上传真实邮件内容；不要让它第一次运行就修改原始邮箱。

可以把下面提示词连同本文交给正在目标电脑上工作的 AI：

```text
请协助我排查 Betterbird/Thunderbird 保存大附件时界面无响应的问题，并在确认兼容性和回退条件后制定升级方案。

第一阶段只读，不修改邮件、Profile、系统配置和启动器：
1. 查询操作系统、桌面会话、CPU 架构和 glibc 版本，与本文的银河麒麟 V11 ARM64、Wayland 环境比较。
2. 确认客户端真实版本、活跃 Profile 和 POP3 mbox 路径，不沿用旧 Thunderbird 副本。
3. 检查进程 CPU、磁盘空间、写入情况、安全软件扫描和临时文件，区分仍在工作与真正死锁。
4. 所有邮件、姓名、地址和附件样例均使用虚构数据，不上传真实邮件或名单。

如果需要应急提取附件：
1. 先完全退出客户端，只读打开 mbox，输出到独立目录。
2. 正确处理 RFC 2047 邮件头，不用中文 grep 作为唯一定位手段。
3. 不编辑原始 Inbox；提取后检查文件大小、SHA-256 和压缩包完整性。
4. 命令或结果与预期不符时立即停止，不自行“修复”邮箱。

如果需要升级：
1. 先从官方来源核对当前程序、ARM64 构建、语言包和扩展兼容性，不照抄旧版本号。
2. 新程序放独立目录，不覆盖旧版本；列出 Profile、密码数据和启动器的备份位置。
3. 给出降级步骤，特别说明 logins.json 跨版本变化的影响。
4. 修改启动器或恢复任何文件前，先等待我确认。
5. 每步完成后验证邮件、中文界面、扩展、附件保存和启动入口；失败立即停止并回退。
```

## 写在最后

这次问题看似只是“44 MB 附件另存为很慢”，实际却穿过了邮件存储、MIME 解析、主线程、下载记录、CPU 占用、安全软件、扩展兼容和 Profile 回退多个层面。

最有效的处理顺序不是先找一个命令重装，而是：

> **先只读拿到附件并验证完整性，再用对照测试缩小根因，最后以旧程序不覆盖、关键配置可恢复的方式升级。**

另外，AI 协助留下的排障笔记也需要公开前复核。本次最重要的修正，就是把“Bug 编号看起来相关”改成“打开官方页面确认它到底修复了什么”。版本号和 Bug 编号都不能代替证据。
