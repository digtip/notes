# Vibe Coding 实战：本地白名单管理系统

有些工具不需要做成平台，也不需要先上一套复杂框架。

日常工作中，我需要持续维护一批通知白名单：新记录分批到来，已有信息偶尔变更，部分记录需要退出，还要按日期整理清单，交给后续审批流程。事情本身不复杂，真正消耗时间的是重复核对：

- 这条记录以前是否录入过？
- 同一批材料里有没有重复项？
- 哪些记录是今天新增的？
- 修改之前有没有备份？
- 导出的表格是不是最新版本？

如果每次都靠手工翻 Excel、复制 Sheet、另存备份，记录越多，越容易在“最后版本”“最终版本 2”之间失去确定性。

于是我用 Vibe Coding 的方式做了一个本地白名单管理工具。它不是演示 Demo，已经投入日常工作使用。后端只有一个 Python 文件，前端是一个 HTML 页面，数据保存在本机，浏览器就是操作界面。

本文对项目做了完整脱敏：不展示真实业务端口、单位、姓名、号码、文件目录和审批信息；示例数据全部为虚构。重点不是公开某套内部系统，而是复盘一种可复用的方法：**怎样把重复、怕错、需要留痕的个人工作，逐步做成真正能用的小工具。**

## 一、先定义问题，而不是先让 AI 写页面

最开始的需求可以浓缩成一句话：

> 把分散到来的名单可靠地维护起来，随时能查、能改、能退出、能导出，而且每次修改都有退路。

进一步拆解后，其实是六个独立问题。

| 工作环节 | 手工操作的风险 | 工具需要提供的能力 |
|---|---|---|
| 批量接收记录 | 格式不统一，容易漏行 | 粘贴解析与逐行预览 |
| 判断重复 | 既可能和历史数据重复，也可能批内重复 | 历史查重与批内查重 |
| 维护已有记录 | 直接改表格，缺少修改时间 | 查询、编辑、批量更新 |
| 记录退出 | 直接删除后难以追溯 | 软删除、退出日期与备注 |
| 提交后续流程 | 手工筛选某一天，容易选错 | 按日期预览并导出 |
| 防止误操作 | 另存文件容易覆盖或漏做 | 每次写入前自动备份 |

这里有一个很重要的经验：**AI 很适合实现功能，但“什么叫做对了”必须由实际使用的人定义。**

如果只输入“帮我做一个白名单管理系统”，AI 很可能给出一个看起来完整、实际却不符合工作习惯的 CRUD 页面。把真实操作中的担心说清楚，才能得到有用的工具。

## 二、最终做出来的工具长什么样

下图来自实际使用的本地系统，展示了工具的真实界面与功能布局。

工具采用三个页面标签，对应实际工作顺序。

### 1. 批量新增

把整理好的文本直接粘贴进去，每行一条记录。系统先不写入，只返回四类结果：

- **新增**：号码有效，且没有与历史记录或本批记录重复；
- **库中已有**：历史数据中已经存在；
- **本批重复**：同一批文本中重复出现；
- **格式错误**：没有识别到符合规则的号码。

只有确认预览后，才执行入库。入库日期默认是当天，也允许按实际批次选择日期。![[vibe-coding-local-whitelist-query.png]]

### 2. 查询与维护

可以按关键字和日期范围筛选，对单条记录进行编辑，也可以批量修改某一字段。修改号码时，服务端再次查重，避免只依赖浏览器页面状态。

记录退出时不做物理删除，而是改为 `removed` 状态，同时保存退出日期和备注。误操作后还可以恢复。

![[vibe-coding-local-whitelist-export.png]]

### 3. 按日期导出

选择日期后，先预览当日新增或退出记录，再生成 Excel。这样“预览”和“导出”使用同一组筛选条件，减少导出后才发现日期选错的情况。

![[vibe-coding-local-whitelist-ui.png]]

## 三、技术选型：够用比“先进”更重要

这个项目没有使用大型 Web 框架，也没有单独部署数据库。

| 层次 | 选择 | 原因 |
|---|---|---|
| 后端 | Python 标准库 HTTP 服务 | 本机运行，依赖少，启动简单 |
| Excel | `openpyxl` | 满足读取、生成和导出需求 |
| 主数据 | 单个 JSON 文件 | 结构清楚，便于备份和检查 |
| 页面 | HTML、CSS、原生 JavaScript | 不需要前端构建链 |
| 使用入口 | 本机浏览器 | 比命令行更适合日常查询和核对 |

整体数据流只有一条主线：

```text
浏览器操作
    ↓ HTTP / JSON
本地 Python 服务
    ↓
JSON 主数据（唯一事实来源）
    ├─ 写入前：备份旧 JSON + 旧 Excel
    └─ 写入后：重新生成在用 Excel
```

#### `test_whitelist.py` 是做什么的

它是**开发后的自动检查工具，不是系统运行必需的组件**。平时使用白名单系统，只需要启动 `本地白名单管理系统.py`，不需要同时运行测试文件。

修改代码后，可以执行：

```bash
python3 test_whitelist.py
```

测试覆盖五项内容：

1. 空目录能否自动创建空白 JSON 和 Excel；
2. 空白 JSON 能否正常初始化；
3. 批量解析能否区分新增、批内重复、库中已有和格式错误；
4. 保存后能否生成 Excel，下次写入前能否备份旧文件；
5. JSON 损坏时能否停止提示，而不是擅自覆盖清空。

测试只使用系统临时目录和虚构号码，不读取、不修改真实白名单。看到 `Ran 5 tests ... OK`，表示五项检查全部通过。

这里最关键的不是 JSON 或 Excel 本身，而是明确：**JSON 是主数据，Excel 是输出结果。**

如果允许用户同时手改两个文件，很快就会出现“到底以哪个为准”的问题。工具规定日常变更都经过页面，Excel 由主数据重新生成，避免双头维护。

## 四、关键实现一：先预览，再写入

批量新增不直接调用保存接口，而是拆成两个步骤：

```text
粘贴文本 → /api/parse → 查看逐行结果 → 确认 → /api/commit
```

号码标准化需要处理从 Excel 复制时常见的小问题，例如数字被读成带 `.0` 的文本、号码两侧有空格等。下面是脱敏后的核心思路：

```python
import re


def norm_phone(value):
    """把输入统一为纯数字文本。"""
    if value is None:
        return ""
    text = str(value).strip()
    if text.endswith(".0"):
        text = text[:-2]
    return re.sub(r"\D", "", text)


def valid_phone(value):
    """本项目的示例校验规则；其他场景应换成自己的业务规则。"""
    return bool(re.fullmatch(r"1\d{10}", value or ""))
```

真正值得保留的是“两阶段设计”，而不是这一段号码规则。换成资产编号、账号、邮箱或其他名单，也同样应该先解析和预览，再允许写入。

### 服务端还要再检查一次

浏览器的预览结果会过期：用户打开页面后，数据可能已经被另一次操作修改。因此提交时不能盲目相信前端传来的 `new` 标记，服务端仍需重新校验格式和重复项。

这是一种很实用的边界意识：

> 前端负责让人看得清楚，后端负责让最后写入的数据仍然符合规则。

## 五、关键实现二：用状态退出，不直接删除

直接删除最省事，却会让“这条记录什么时候退出、为什么退出”无从追查。

项目采用软删除，记录中保留这些字段：

```json
{
  "id": 1,
  "name": "示例人员甲",
  "phone": "13800000001",
  "company": "示例单位 A",
  "addDate": "2026-01-15",
  "status": "removed",
  "removedDate": "2026-02-01",
  "removedNote": "示例：因业务调整退出",
  "updatedAt": "2026-02-01T10:30:00"
}
```

在用清单只输出 `active` 记录；历史数据仍保留在 JSON 中。恢复误退记录时，把状态改回 `active`，并清空本次退出信息。

软删除不是“永远不删数据”的理由。真实场景仍需根据制度确定保留期限、备份数量和销毁方式，不能无限积累敏感数据。

## 六、关键实现三：每次写入前自动备份

每次新增、编辑、退出、恢复或批量更新之前，程序都会备份当时的 JSON 和 Excel，文件名带时间戳；同一秒发生多次操作时追加序号，避免覆盖。

流程如下：

```text
收到写请求
  → 校验请求
  → 备份当前文件
  → 写入主数据
  → 重新生成 Excel
  → 返回结果与备份文件名
```

自动备份解决的是“改错了还能找到上一版”，但它不等于完整的数据安全方案：

- 备份与主数据放在同一块磁盘上，不能抵御磁盘损坏；
- 没有定期清理策略，备份目录会不断增长；
- 含敏感信息的备份与主数据同样需要访问控制；
- 当前实现不是数据库事务，异常中断后仍要检查文件完整性。

因此，正式使用时还应增加异地或离线副本、恢复演练、保留周期和必要的加密措施。

## 七、Vibe Coding 的正确打开方式：一轮只解决一个闭环

这个项目不是一次提示词生成的。更可靠的方式，是按可验证的小闭环逐步推进。

### 第一轮：只做数据模型和导入预览

先让 AI 读取虚构样例，输出解析结果，不允许写文件。确认四类状态符合预期后，再进入下一轮。

### 第二轮：加入主数据和查重

明确唯一键、字段含义、空值处理和历史数据初始化方式。用“历史重复、批内重复、非法输入、空行”构造测试。

### 第三轮：加入编辑、退出和恢复

重点检查状态变化，而不是只看按钮是否出现。尤其要验证重复退出、恢复在用记录、修改成已存在号码等边界情况。

### 第四轮：加入导出

预览与导出必须复用同一筛选条件，并核对空结果、跨日期批次和中文文件名。

### 第五轮：最后再做界面和易用性

统计卡片、分页、弹窗、按钮状态都很有用，但它们应该建立在稳定的业务规则之上。否则很容易得到一个漂亮但不可信的页面。

## 八、真实使用后，最值得保留的设计

### 1. 默认日期减少重复选择

大多数新增和退出都发生在当天。默认填入当天日期，需要处理历史批次时再修改，比每次手选更顺手。

### 2. 导出之前必须先看到数量

“当日新增 0 条”和“导出成功”不是一回事。先显示记录数和明细，再允许下载，能避免拿着空表进入后续流程。

### 3. 主数据与交付文件分开

内部管理需要姓名、备注、状态和更新时间；对外导出可能只需要其中一列。工具按用途生成不同文件，而不是把整张主表交出去，能天然减少不必要的数据暴露。

### 4. 备份动作自动化

依赖人记得备份，迟早会漏。把备份放到每次写入之前，比在使用说明里写一句“请注意备份”可靠得多。

## 九、安全边界：个人效率工具不等于可直接开放访问

本文提供的通用版本定位为单用户、本机运行的个人效率工具，默认仅监听 `127.0.0.1`。它尚未提供用户认证、权限控制、并发事务和操作审计，因此不应未经安全改造就直接暴露到局域网或公网。若需要多人共享使用，应进一步引入数据库与唯一约束、身份认证、访问控制、操作审计和独立备份机制。

### 1. 默认只监听本机

如果服务监听 `0.0.0.0`，同一网络中的其他设备可能访问页面和接口。名单类数据通常具有敏感性，没有身份认证、访问控制和加密传输时，不应直接提供局域网访问。

更稳妥的默认方式是：

```python
# 只允许本机浏览器访问
server = ThreadingHTTPServer(("127.0.0.1", 8210), Handler)
```

确有共享需求时，不应只改一个监听地址，而要重新设计登录认证、权限、审计、传输加密和并发控制。

### 2. JSON 不适合多人并发写入

当前设计面向单用户、低频率操作。多人同时写入需要数据库事务、唯一约束和冲突处理，不能靠多线程 HTTP 服务解决。

### 3. 不要把真实名单发给公共 AI

让 AI 协助开发时，应使用虚构数据。真实姓名、号码、单位、账号和业务清单不应粘贴到公共对话或上传到在线代码工具。

### 4. 导出文件仍需按原流程审批

工具只负责减少整理错误，不会替代人工审核、权限审批和提交流程。导出完成不等于业务操作已经完成。

## 十、如果重新做一版，我会优先补什么

目前版本已经满足个人日常使用，但如果要扩大使用范围，优先级应该是：

1. **自动测试**：覆盖解析、查重、状态转换、导出和备份恢复；
2. **异常恢复与完整性检查**：在现有 JSON 原子替换基础上，补充异常中断后的检查与恢复流程，并定期演练备份恢复；
3. **备份保留策略**：按时间和数量轮换，并定期验证能够恢复；
4. **操作日志**：记录谁在何时做了什么，而不只是保存数据字段；
5. **数据库与唯一约束**：多人使用时迁移到 SQLite 或其他数据库；
6. **认证与授权**：有共享需求时再加用户、角色和访问控制。

顺序不能反：先保证数据正确和可恢复，再增加协作能力。

## 十一、这套方法还能用在哪些工作里

只要满足“数据量不大、规则比较明确、重复操作多、错误代价高”，就可以考虑类似的本地工具：

- 账号申请材料的登记与去重；
- 设备资产的新增、借出、归还和导出；
- 证书或许可证到期清单维护；
- 批次文件的接收、校验和交付记录；
- 周期性报表的数据汇总与格式检查。

它们的页面不同，底层闭环却很相似：

> 输入标准化 → 预览校验 → 人工确认 → 单一主数据 → 状态留痕 → 定向导出 → 自动备份。

## 十二、把项目交给 AI 协助实施：提示词模板

> [!important]
> 建议先让 AI 用虚构数据搭建并测试，不要直接提供真实名单，也不要让它第一次运行就修改正式文件。

```text
请协助我做一个本地白名单管理工具，用于减少 Excel 重复登记和手工核对。
第一阶段只做只读分析和数据模型设计，不要创建或修改真实业务文件。
先检查本机 Python 版本、工作目录、现有文件和端口占用，与本文所述环境比较；路径、端口等参数按本机实际情况替换，不直接照搬。

功能要求：
1. 支持批量粘贴文本，解析后先预览，再人工确认入库。
2. 区分历史重复、本批重复、格式错误和可新增记录。
3. 支持关键字和日期查询、单条编辑、批量修改。
4. 退出采用软删除，保存退出日期与备注，并支持恢复。
5. 按日期预览并导出新增/退出 Excel。
6. 每次写入前备份旧主数据和旧导出文件。
7. JSON 是唯一主数据，Excel 只是生成结果，不允许双头维护。

安全要求：
1. 所有示例姓名、号码和单位必须使用虚构数据。
2. 默认只监听 127.0.0.1，不提供无鉴权的局域网访问。
3. 不连接真实业务接口，不自动提交审批，不上传数据。
4. 修改正式文件前先给我备份位置和恢复步骤，并等待确认。
5. 每次只完成一个可验证闭环，先测试再进入下一项。
6. 任一结果与预期不符立即停止，不自行改变业务规则。

请先输出：
- 数据字段和状态说明；
- 文件清单；
- 测试用例；
- 风险与回滚方案。
```

## 写在最后

Vibe Coding 的价值，不是让 AI 一口气生成几千行代码，而是让一个最了解工作痛点的人，能够更快把经验变成工具。

这个项目没有复杂技术栈，真正起作用的是几件朴素的事：写入之前先预览、主数据只有一个、退出不抹掉历史、导出之前先核对、修改之前自动备份。

**先把工作里的不确定性消灭掉，再谈页面有多漂亮、框架有多先进。** 对个人效率工具来说，这已经足够有价值。
